# Deliver an agreed data slice

Implement the smallest valuable slice, not a generic framework. First read approved design decisions and inspect the relevant code and environment. If a consequential choice is unresolved, use `forge-de-design` (or its sibling `SKILL.md`) to discuss trade-offs and confirm the affected stage **before writing that stage's design document**. Do not demand documentation for a small fix when behavior is already agreed; do not silently invent a business definition or source authority.

## Delivery loop

1. **Define the authorized change.** The user's explicit implementation request authorizes only its stated local scope. Summarize what will change, what will not, dependencies, acceptance checks and any assumptions. For significant code changes, use the host's planning/approval flow. Review existing files before overwriting.
2. **Check environment and permissions.** Confirm source access, target environment, data sensitivity, credentials boundary and operational owner. Do not copy raw private rows or secrets into logs, prompts or docs. Use synthetic test fixtures by default; use real-derived test data only after permitted use, de-identification/re-identification risk and storage/access controls are explicitly verified and approved. Check current vendor documentation if a changing API, cost or platform-specific behavior matters; delegate to a specialized platform skill when appropriate.
3. **Build with existing conventions.** Prefer a reversible, idempotent, observable path. Include explicit grain/keys, schema-change behavior, retries, duplicate/delete/late-data handling and backfill boundaries to the degree the slice requires. For custom ingestion code/connectors and pipeline/infrastructure/configuration artifacts managed as code, use the project's version control, review, automated tests and deployment process where supported; for managed-product settings, follow an auditable change process. Keep source/destination dependencies explicit and loosely coupled where this aids safe change. Minimize sensitive fields at ingestion and avoid copying them into logs or ordinary development fixtures. Avoid unneeded distributed infrastructure and vendor lock-in. Do not create unapproved design notes or status files as a side effect.
4. **Verify locally first.** Use deterministic synthetic fixtures by default and unit/integration checks; distinguish read-only inspection from tests that write data. If verified and approved de-identified real-derived data is necessary, use only the minimum fields in a controlled location. Compare actual results with the agreed contract, including representative edge cases and failure recovery. Do not claim a run passed if it was not run.
5. **Gate external effects.** Before executing a remote job, changing cloud resources, writing production data, incurring meaningful cost, deleting or overwriting data, explain exact target, side effects, rollback and verification; get the required explicit confirmation. A design sign-off is not that confirmation. Access to sensitive production data for debugging is an exceptional action: follow the organization's policy for the required authorized approver(s), issue-specific minimum scope, and expiry; if the applicable authority or boundary is unclear, stop and ask the responsible security/privacy owner. If access or evidence is missing, stop at a safe local test and report the limitation.
6. **Report evidence.** State files/resources changed, checks run and their results, remaining risks, deviations from the agreed design, and the next narrow step. If a test fails, diagnose without concealing the failure; seek consent again for a revised consequential action.

See [delivery-checks.md](references/delivery-checks.md) for proportional coverage by pipeline shape. For ingestion implementation, compare the approved behavior with the approved design contract; use Chapter 7 trade-off guidance from the optional `forge-de-design` skill if installed. For query/model/transform behavior, follow the approved contract and use Chapter 8 context from `forge-de-design` if installed to derive fit-for-purpose tests. For serving contracts, ML handoffs, freshness/status acceptance, and reverse-ETL write boundaries, follow the approved contract; the optional `forge-de-design` skill has related Chapter 9 context. For approved security/privacy/governance requirements, use the optional `forge-de-operate` skill for relevant control evidence and test boundaries when installed; do not substitute this build check for legal review or ongoing operational control. Translate only relevant cases into synthetic/local checks before considering external execution. Hand continued quality/SLO monitoring, access review, incident readiness, and control maintenance to the optional `forge-de-operate` skill when installed; otherwise hand off to the project's operational owner. Stage approvals govern **design documents**; a separate implementation request governs **code**; remote side-effect approval governs **deployment and execution**. Keep these three permissions distinct.
