# Co-design a data system

A technically polished solution can fail if it optimizes a metric nobody uses. Work backward from a decision or consumer, then choose the simplest architecture that meets the agreed constraints. Use [stages.md](references/stages.md) for questions and exit criteria, [decision-lenses.md](references/decision-lenses.md) when options matter, and [documentation.md](references/documentation.md) **only after the relevant stage is approved**.

## Conversation loop for each relevant stage

1. Establish the **current slice and stage** from the user's request and any approved project context. Read code, schemas, existing agreements, or safe metadata when useful. Do not retrieve sensitive rows or use production writes as discovery. If access is missing, state what cannot be verified and propose a safe path; do not assume permission.
2. Ask only questions that change a decision. Surface definitions, ownership, freshness, volumes, failure tolerance, security, budget, team skills, and operations where material. If the user supplied answers, reuse them. Seek upstream and consumer input when the user can obtain it; do not invent stakeholder approval.
3. Compare 2–3 viable options **when a real choice exists**. Explain the benefit, cost/complexity, failure mode, reversibility, and conditions favoring each. Recommend one with assumptions and a cheap way to validate them. For a constrained or obvious choice, state the rationale without manufacturing alternatives. See [decision-lenses.md](references/decision-lenses.md).
4. In chat, summarize what is known, what is inferred, the proposed decision and its consequences, acceptance criteria, and any unresolved blocker. Ask the user to **confirm the decision and its scope for this stage**. A tool preference, silence, or approval for a prior stage is not this confirmation. If the user disagrees, revise and continue the conversation; do not rush to a document.
5. Only after explicit confirmation, create or update **that stage's** design document in the target project's repo if documentation is wanted as part of the agreed workflow. Read [documentation.md](references/documentation.md). Keep unapproved stages in chat, not placeholder files, ADRs, memory, or status files. A later change to an approved decision reopens the affected part before rewriting it.
6. Offer the next smallest useful stage or proof of value. Stages overlap; a narrow slice may need decisions from several stages at once. Group the relevant decisions in one review if that reduces churn, but label each and obtain explicit approval for each stage you will document.

## Five decision areas, not a rigid sequence

For business framing and the maturity lens, read [01-business-value-and-data-maturity.md](references/01-business-value-and-data-maturity.md) when starting an initiative. For lifecycle tracing or cross-stage handoffs, read [02-lifecycle-and-undercurrents.md](references/02-lifecycle-and-undercurrents.md). For system boundaries, architecture principles or pattern comparisons, read [03-architecture-principles-and-patterns.md](references/03-architecture-principles-and-patterns.md). For comparing concrete technologies after the architecture is understood, read [04-technology-selection.md](references/04-technology-selection.md). For source behavior, ownership, constraints and producer agreements, read [05-source-generation-and-contracts.md](references/05-source-generation-and-contracts.md). For storage guarantees, access patterns, abstractions and lifecycle, read [06-storage-and-data-layout.md](references/06-storage-and-data-layout.md). For choosing ingestion patterns, source-change capture, cadence, buffering and recovery requirements, read [07-ingestion-patterns-and-recovery.md](references/07-ingestion-patterns-and-recovery.md); keep connector implementation and operational verification in the delivery skill. For query workloads, data grain/models, transformation/persistence semantics and the Design-to-Build handoff, read [08-query-modeling-and-transformation.md](references/08-query-modeling-and-transformation.md). For consumer-facing serving contracts, serving-mode trade-offs, analytics/self-service, ML data handoffs, and reverse ETL/writeback boundaries, read [09-serving-contracts-and-data-products.md](references/09-serving-contracts-and-data-products.md). Use it for design and handoff questions; keep implementation in the build skill. For cross-lifecycle security, privacy, governance, data minimization, access-control, retention/deletion, or incident-readiness requirements, hand off to the optional `forge-de-operate` skill for its detailed reference when installed; identify the relevant owner either way. Legal duties and remote side effects retain their separate approvals. Load other references only when relevant to the current decision.

- **Outcome and consumer:** business action, stakeholders, KPI semantics and grain, required freshness, success measures.
- **Sources and feasibility:** generation, owners/rights, source quality, change patterns, sensitivity and contracts.
- **Architecture and modeling:** storage/compute, conceptual/logical/physical model, keys and grain, recoverability, cost and scale.
- **Data flow and authoritative meaning:** ingestion, transformation, incremental/backfill/replay, deduplication, canonical datasets and metric definitions.
- **Serving and operations:** interfaces for analysts/apps/ML, access and self-service, quality/SLO/observability, incidents, lineage, governance and improvement.

Security/privacy, data management, DataOps, architecture, orchestration, and software engineering cut across all five. Raw/staging/curated is useful when isolation and stewardship warrant it; it is not a universal three-layer requirement. “Single source of truth” can mean an authoritative **definition and owner**, not one giant central storage system. See [sources.md](references/sources.md) for conceptual attribution to the book and the user's workflow.

Do not turn a design approval into permission to deploy, schedule jobs, modify remote resources, or incur cost. Hand explicit implementation requests to `forge-de-deliver` (or its sibling `SKILL.md` if skill invocation is unavailable).
